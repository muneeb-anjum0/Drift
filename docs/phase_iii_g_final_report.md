## Current pipeline and product error model

```text
authenticated client/project/version → immutable requirement snapshot
  → R5 lexical/domain scoring + specific-match/0.25 threshold + stable top-3
  → sequential P1 six-class llama.cpp call per selected requirement
  → inference JSON normalization → Go normalization → PP1 preview/score
  → separate authorized Save of submitted analysis
```

Go checks actor capability and project/version before Analyze; FastAPI formats the unchanged P1 single-pair prompt and calls the existing 7B Q4_K_M llama.cpp service. The current CPU server has one slot, context 768, generation cap 120, `--n-gpu-layers 0`, and `--device none`; model SHA256 is `11e2ca8d10f6b52693256addca9b8f0d5bb01eebc53594b531586ea992419ac9`. Current latency is approximately `T_R5(N) + Σ T_P1(pair_i) + T_normalize + T_PP1 + network`, for 0–3 selected candidates; if no candidate is selected, Go creates a new-requirement preview without calling the model. This is an operational formula, **not** a measured full-product SLA. New-requirement fallback means a zero-target retrieval case is not automatically a “no drift” product case.

The distinct failure classes are: missed relevant requirement before classification; irrelevant exposure/call; incorrect P1 affectedness or six-class label; malformed/partial/foreign-ID model output; normalization or PP1 error; and authorization, tenant, version, Save, or UI workflow error. A false retrieval exposure costs CPU time but becomes a false final drift only if downstream processing promotes it. A retrieval miss cannot be repaired by a perfect classifier because no pair is sent. Product cost of missed changes, false human review, timeouts, and monetary value are UNKNOWN; no invented weighted score is used. Security-critical actor/project/version checks and persistence remain server-owned, never model-owned.

The existing 90% overall and 85% medium/large retrieval gates remain unchanged. They protect model-input coverage and are not made irrelevant by batching. A future end-to-end gate should jointly measure final affected-requirement recall, complete-message correctness including all targets and no false final drift, six-class quality, strict contract/ID validity, zero-target/new-requirement handling, project-size slices, latency/calls/tokens, and tenant/workflow invariants. Numeric final-product false-drift and latency tolerances require product review and an independently reviewed end-to-end holdout; no replacement gate was frozen here.

## Decision, retraining, and remaining evidence

No architecture reaches a defensible development Pareto point across **complete-message coverage, false-final-drift control, structural validity, latency, calls, and project scale**. Top-5 ranking has more retrieval coverage but sharply more exposures; the measured batch rejector fails its fundamental exact-ID contract and can miss an already-retrieved target. Whole-baseline processing is context-infeasible beyond small short baselines; hierarchy lacks source structure; model-side selection and decomposition+batch have unmet prerequisites. Accordingly **no pipeline candidate identity was assigned or frozen, no new independent holdout was created or reviewed, and no blind final baseline/candidate evaluation was run**. The historical III-D/E sets were not reused. Final Phase III-G conclusion: **NO PIPELINE ARCHITECTURE YET SUPPORTED**. This does not assert generalisation supported or not supported for an uncreated candidate.

**RETRAINING NOT YET JUSTIFIED.** The panel separates one missed target at retrieval, one semantic label error on a reached target, two false candidate drift labels, and multiple batch-format failures. That is actionable diagnosis, not repeated independently reviewed post-oracle classifier failure after a reliable retrieval path. No training proposal was authorized, no GPU was used, and R5/R6 were not promoted. The next phase should first design a deterministic, strict-ID multi-item contract and independently review product-level error costs; any materially improved development winner must be frozen before a genuinely new reviewed holdout. Do not lower the existing retrieval gate merely because broad batches might eventually be cheap.
