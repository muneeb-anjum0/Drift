# Distribution and Deployment Boundaries

## Validated local-first path

`LOCAL_FIRST_DISTRIBUTION` is the supported direction: a private Linux x86-64 Docker Compose installation bound to localhost, with the original GGUF supplied separately when AI comparison is needed. A fresh-clone model-free stack, Chromium workflow, data persistence, synthetic Mongo backup/restore, and a bounded original-GGUF CPU smoke were verified in Phase IV-G; see [research history](research-history.md). Windows/macOS and end-to-end NVIDIA GPU operation were **not verified**. The local Compose stack is not a hardened public deployment. Follow [development](development.md) for normal installation; do not expose its ports to the Internet.

## Proposed staging, not completed hosting

`docker-compose.yml` plus `docker-compose.staging.yml`, `.env.staging.example`, `tools/verification/check_staging_env.py`, and `deploy/staging-ingress.nginx.example.conf` define a **separate staging design**. They do not prove that a host, DNS, TLS certificate, firewall, monitoring, off-host backup, or public route exists. Compose v2.24.4+ is needed for the staging overlay's `!override`/`!reset`. A staging release requires a reviewed clean source SHA in `STAGING_RELEASE_ID`, recorded immutable image digests, independently generated secrets, and operator-owned host/data custody. The example env intentionally cannot pass preflight unchanged. Never commit `.env.staging` or publish expanded `docker compose config` output: it can expose secrets.

Staging is a dedicated `drift-staging` Compose project with internal `drift_staging` Mongo, separate named Mongo/report volumes, synthetic/test data initially, uploads disabled, and a separate original GGUF host copy mounted read-only. The backend URI is fixed to the in-project database—not a configurable production URI. The example model file belongs outside the source tree and must match SHA-256 `11e2ca8d10f6b52693256addca9b8f0d5bb01eebc53594b531586ea992419ac9`. No rejected candidate or final-holdout material belongs on the host. Optional future GCS uploads require a staging-only bucket, least-privilege service account, independent object backup/restore, and separate approval. Local Firebase/GCS setup is optional and has not been validated against a real disposable bucket here.

Staging env separates frontend HTTPS origin, same-origin `/api/v1`, Mongo credentials, JWT secret, inference key/endpoint, provider master key if BYOK is enabled, model path, storage, CORS, trusted proxy CIDR, rate limits, logging, and ports. The frontend HTTP binding is loopback pending an external TLS terminator. Ingress should route `/api/` directly to Go and `/` to frontend; it must overwrite client-supplied `X-Forwarded-For`, occupy the explicitly configured network IP, redirect HTTP, and emit HSTS only on HTTPS. No backend, inference, llama, or Mongo port is published to the host by the staging overlay. A static template or local network test is not a real certificate, DNS, firewall, TLS, or trusted-proxy validation.

## Host and release gate

Before any controlled public/staging deployment, verify dedicated host CPU/RAM/disk against the 4.36 GiB GGUF and 7 GiB llama container limit, read-only artifact custody, Docker/Compose version, model load, TLS/DNS/firewall, exact ingress-to-Go peer identity, explicit CORS, real staging secrets, image digests, authenticated service routes, Mongo index compatibility, synthetic product workflow, off-host backup/retrieval, alert delivery/retention, and target-host rollback. Container CVE scanning remains a gate where available. A local PASS does not become a target-host PASS. Stop on incompatible indexes; automatic reverse schema migration is not available. No public staging deployment is claimed or authorized by this guide.

For staging preflight on an authorized host, first inspect a **sanitized** configuration and run `python3 tools/verification/check_staging_env.py --env-file .env.staging`; then render `docker compose --env-file .env.staging -f docker-compose.yml -f docker-compose.staging.yml --profile model config --quiet`. Do not run this against production credentials or data. Deployment itself requires a separate reviewed authorization.

## Recovery boundary

Retain the prior reviewed Git SHA, image digests, matching encrypted configuration snapshot, verified original GGUF, and tested Mongo backup before rollout. A failed release closes traffic; restore the previous compatible frontend/backend/inference images **without rebuilding from mutable inputs** and verify hashes and readiness. Keep the Mongo volume intact for an application rollback. A data restore requires halted writes, a fresh snapshot of failed state, an isolated restore check of IDs/counts/indexes, and explicit operator approval. Never use broad volume pruning or the rejected candidate as a rollback artifact. The Phase IV-C A→B→A exercise proved local orchestration mechanics with synthetic data, **not** binary compatibility of real releases or target-host rollback. Detailed backup, monitoring, and failure signals are in [operations](operations.md).
