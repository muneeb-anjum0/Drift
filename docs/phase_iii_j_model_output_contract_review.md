# Phase III-J Model Output Contract Review

## 1. Status

Architecture review only; no contract or implementation change is authorized by this document. The Phase III-J adapter is rejected: development generation had 0/124 structurally valid outputs and the development-only raw probe had 0/12. The masked-placeholder corrective proposal was withdrawn after its teacher-forcing audit (`docs/phase_iii_j_baseline_outcome.md`; `docs/phase_iii_j_structural_failure_probe.md`; `docs/phase_iii_j_corrective_training_proposal.md`). No corrective training or promotion has occurred. The sealed final holdout remains outside this review.

## 2. Current Contract

The current P1 prompt asks a causal LM for JSON containing exactly `label`, `confidence`, `reasoning`, and `changed_elements` (`services/inference/runtime.py:45-65`; `evaluation/prompts/P1.json`). PEFT generation and GGUF completion produce text, which is parsed into a four-field `DriftPrediction`; the FastAPI `/predict-drift` endpoint exposes that schema (`services/inference/runtime.py:263-311`; `services/inference/contracts.py:30-85`; `services/inference/app.py:100-110`). The parser tolerates extracted/wrapped JSON and some type normalization; this is *not* evidence that the four values are valid semantic targets. Go separately decodes and validates the four fields, then either returns them on its direct-analysis route or transforms them into requirement-level analysis and detected changes (`server-go/internal/modules/drift/inference_client.go:77-134`; `server-go/internal/modules/drift/drift_handler.go:25-60`; `server-go/internal/modules/drift/drift_service.go:144-198`). A project preview may subsequently be saved as a `DriftAnalysis` document; direct analysis alone is not that save operation (`server-go/internal/modules/drift/drift_service.go:578-635`).

The contract is currently a *multi-output generative* contract even though the underlying product decision is a six-class relationship classification. Structural validity and semantic correctness are separate questions.

## 3. Field-by-Field Evidence

### label

**Producer and authority.** The model generates one of `added`, `modified`, `removed`, `contradiction`, `ambiguous`, or `unchanged`; these are the only reviewed target values in Phase III-J (`services/inference/contracts.py:30-34`; `tools/phase3j_kaggle/phase3j.py:180-219`; `evaluation/phase_iii_j/frozen/reviewed_train_v1.json`; `evaluation/phase_iii_j/frozen/reviewed_development_v1.json`). The review decisions are AI-authored/AI-reviewed, not independent human gold labels (`docs/phase_iii_j_methodology_deviation.md:1-9`).

**Validation and use.** FastAPI canonicalizes and validates the label, and Go validates it again (`services/inference/contracts.py:61-63`; `server-go/internal/modules/drift/inference_client.go:113-134,168-175`). Go may override `added`/`modified` to `unchanged` for a report-access special case; this confirms Go, not the model, has final domain authority (`server-go/internal/modules/drift/drift_service.go:207-228`). `unchanged` suppresses a detected change; other labels become `ChangeType`, enter impact/effort/recommendation and score logic, and are saved with requirement results and detected changes (`server-go/internal/modules/drift/drift_service.go:151-175,266-283,578-610`; `server-go/internal/modules/drift/inference_client.go:177-201`; `server-go/internal/modules/drift/drift_model.go:9-22,51-107`; `server-go/internal/modules/drift/drift_scoring.go:8-87`). Go also has a rule-based path and a no-relevant-requirement heuristic, so not every displayed label comes from the model (`server-go/internal/modules/drift/drift_service.go:54-73,129-141`). The direct API and client display the raw label; project analysis displays/saves it via results and changes (`server-go/internal/modules/drift/drift_handler.go:25-90`; `client/src/features/drift/drift.types.ts:8-20,31-41,95-100`; `client/src/features/drift/DriftAnalysisPanel.tsx:326-379`). This is the core product decision, not mere metadata.

### confidence

**Producer and supervision.** The current model *generates a number in JSON*. Neither reviewed train nor development decisions contain reviewed confidence targets. The prompt and parsers impose a range, not a meaning or correctness calibration (`evaluation/prompts/P1.json`; `services/inference/contracts.py:32,64-68`; `server-go/internal/modules/drift/inference_client.go:99-134`). The GGUF request reads completion text only, and the PEFT path reads generated token IDs only: neither exposes candidate-label probabilities or scores in the present runtime (`services/inference/runtime.py:263-311`). **confidence is not currently a scientifically defined model output.** It is neither an observed correctness probability nor a calibrated classifier score; other rule-based paths use heuristic scores (`server-go/internal/modules/drift/drift_service.go:519-575`).

**Consequences.** Go suppresses non-`unchanged` predictions below 0.35, converts retained values to integer percentages (even zero becomes one), records them in requirement results/detected changes, aggregates them, and displays them (`server-go/internal/modules/drift/drift_service.go:151-175`; `server-go/internal/modules/drift/inference_client.go:177-201`; `server-go/internal/modules/drift/drift_model.go:9-22,51-60`; `server-go/internal/modules/drift/drift_postprocess.go:269-295`; `client/src/features/drift/DriftAnalysisPanel.tsx:326-372`; `client/src/features/drift/DetectedChangeCard.tsx:13-32`). The direct API exposes it, and the legacy benchmark uses it for thresholds and aggregate reporting (`server-go/internal/modules/drift/drift_handler.go:25-60`; `server-go/internal/modules/evaluation/evaluation_benchmark.go:213-280`; `server-go/internal/modules/evaluation/evaluation_model.go:12-26,58-70`). It affects behavior materially despite lacking calibration.

**Possible future score.** A classifier's six candidate-label scores could in principle be obtained from token log probabilities or a classification head, but the present code does not do that. A normalized class score is not automatically a probability that the answer is correct; scoring protocol, held-out calibration data, reliability/error analysis, and threshold validation would be necessary before calling it confidence or reusing the 0.35 filter. The 477/124 AI-reviewed train/development partition is finite and provenance-limited; it cannot simply be used both to fit a calibration function and claim an independent calibrated evaluation. The sealed final is not calibration data. Transformer generation can expose token scores when specifically requested ([Hugging Face generation API](https://huggingface.co/docs/transformers/main_classes/text_generation)); calibration remains an empirical requirement ([Guo et al., 2017](https://proceedings.mlr.press/v70/guo17a.html)).

### reasoning

**Producer and supervision.** The model generates a free-text explanation. The Phase III-J reviewed targets contain no reviewed P1 `reasoning` values. Some review decisions include an adjudication `reason` (44/477 train; 16/124 development), but those are sparse review notes, not complete model-output explanations and must not be relabeled as such (`evaluation/phase_iii_j/frozen/reviewed_train_v1.json`; `evaluation/phase_iii_j/frozen/reviewed_development_v1.json`). FastAPI bounds it and Go requires/bounds it; neither verifies factual entailment (`services/inference/contracts.py:57-85`; `server-go/internal/modules/drift/inference_client.go:99-134`). Existing evidence reports a fabricated conflict rationale and misleading explanations (`docs/phase_iii_final_report.md:33-34`). A fluent explanation could rationalize a wrong label.

**Consequences.** Go stores it in `RequirementAnalysisResult.Reasoning`; it becomes a detected change's `Description` and may become the analysis summary, with no-change summaries also able to include it (`server-go/internal/modules/drift/drift_service.go:151-198`; `server-go/internal/modules/drift/inference_client.go:192-200`; `server-go/internal/modules/drift/drift_model.go:51-60`; `server-go/internal/modules/drift/drift_postprocess.go:176-223`). Description participates in grouping/canonicalization and may affect drift scoring, so it is not purely cosmetic (`server-go/internal/modules/drift/drift_postprocess.go:254-322`; `server-go/internal/modules/drift/drift_scoring.go:68-71`). Saved change-request drafts reuse change titles/descriptions (`server-go/internal/modules/change_request/change_request_service.go:39-104`). Frontend project cards and the direct test panel display it (`client/src/features/drift/DriftAnalysisPanel.tsx:326-379`; `client/src/features/drift/DetectedChangeCard.tsx:13-32`). Users need an intelligible, traceable basis for a decision; the source does not establish a need for an *unsupervised model-generated* rationale. Removing it without replacing the dependent summaries/descriptions would change product behavior.

### changed_elements

**Producer and supervision.** The model generates a string array, but reviewed Phase III-J data provides no element lists, span annotations, extraction rubric, or reviewed target values (`evaluation/phase_iii_j/frozen/reviewed_train_v1.json`; `evaluation/phase_iii_j/frozen/reviewed_development_v1.json`; `evaluation/prompts/P1.json`). The prompt calls for an array but does not settle whether an element is an exact diff span, semantic feature, affected entity, or explanation phrase. Current use suggests an untyped *salient title/impact hint*, not a proven exact diff. FastAPI and Go constrain shape/size, not semantic provenance (`services/inference/contracts.py:72-85`; `server-go/internal/modules/drift/inference_client.go:99-134`). Earlier evidence explicitly left changed-element set quality unverified (`docs/phase_iii_final_report.md:33`).

**Consequences.** Go uses the joined list in impact heuristics and its first item as a preferred change title; title and impact then affect scores, recommendations, saved drafts, and UI. The raw list is shown by the direct API/UI but is not a first-class field on saved `DetectedChange` or `RequirementAnalysisResult` (`server-go/internal/modules/drift/inference_client.go:177-201`; `server-go/internal/modules/drift/drift_scoring.go:8-87`; `server-go/internal/modules/drift/drift_model.go:9-22,51-60`; `server-go/internal/modules/change_request/change_request_service.go:70-104`; `client/src/features/drift/DriftAnalysisPanel.tsx:326-342`). Thus the field has operational effects while being treated as a generated suggestion without extraction evidence. A separate, specified extraction task or transparent deterministic source-text derivation could be considered later; existing reviewed labels alone are insufficient to train or validate it.

## 4. Available Supervision

The frozen reviewed train/development sets contain 477/124 six-class `reviewed_label` decisions, with case metadata and some review notes, but no per-case reviewed confidence, P1 reasoning, or changed-element annotations (`evaluation/phase_iii_j/frozen/reviewed_train_v1.json`; `evaluation/phase_iii_j/frozen/reviewed_development_v1.json`). The existing training encoder deliberately supervises only the label continuation after a `{"label":"` prefix, while the development evaluator demands strict four-field output (`tools/phase3j_kaggle/phase3j.py:171-219,253-273`). The attempted synthetic masked-value repair was withdrawn because masked placeholder text still conditions subsequent supervised tokens (`docs/phase_iii_j_corrective_training_proposal.md`). Reviewed *label* does not imply reviewed *confidence, explanation, or extraction*.

## 5. Current Downstream Dependencies

The actual path is model text → FastAPI parser/schema → Go strict decoder → relevance selection and domain normalization → change conversion/thresholding → `CleanAnalysis`/scoring → preview/direct API → optional save → saved-analysis and change-request consumers (`services/inference/runtime.py:263-311`; `services/inference/contracts.py:30-85`; `services/inference/app.py:100-110`; `server-go/internal/modules/drift/inference_client.go:77-134`; `server-go/internal/modules/drift/drift_service.go:34-198,578-635`; `server-go/internal/modules/drift/drift_postprocess.go:176-322`; `server-go/internal/modules/change_request/change_request_service.go:39-104`). `label` controls classification/change existence. `confidence` controls a hard filter and is persisted/displayed. `reasoning` becomes persisted user-facing text and may influence grouping/score. `changed_elements` is not saved raw but influences persisted title/impact. API exposure includes the direct four-field object and project analysis preview/history; client types and views assume numeric confidence and textual reasoning (`server-go/internal/modules/drift/drift_handler.go:25-119`; `client/src/api/drift.api.ts:5-50`; `client/src/features/drift/drift.types.ts:8-100`; `client/src/features/drift/DriftAnalysisPanel.tsx:221-379`; `client/src/features/drift/DriftHistory.tsx:81-90`). These are genuine dependencies, not proof the fields should remain model outputs. The save path accepts client-returned preview fields and recomputes analysis, rather than rerunning inference, so any migration must preserve authorization and validation of submitted data (`server-go/internal/modules/drift/drift_service.go:578-610`).

## 6. Task-Type Assessment

The semantically supervised Phase III-J task is **A: six-class classification** on a baseline requirement and client message. The present P1/output contract asks for **C/D: classification plus an uncalibrated numerical assertion, explanation generation, and changed-element extraction**. Product-level presentation is a mixture because Go computes relevance, heuristics, scoring, titles, summaries, and drafts. **Yes: the current four-field contract asks the model to solve more tasks than the reviewed dataset actually supervises.** Requiring complete four-field JSON in the frozen development evaluator while training only a label is a direct output-contract mismatch, not evidence that the label classification problem itself requires four generative outputs (`tools/phase3j_kaggle/phase3j.py:171-219`).

## 7. Architecture Options

| Option | Semantic/evaluation fit | Product and migration consequence | Assessment |
| --- | --- | --- | --- |
| A — Label-only model, e.g. `{"label":"removed"}` | Matches available reviewed target; strict one-field parsing is testable and auditable. | Breaks today's Go decoder, confidence gate, descriptions, title hints, direct/UI types, and old four-field gate until versioned consumers are redesigned. | Correct *model* responsibility; not a drop-in API replacement. |
| B — Label plus separately derived calibrated confidence | Potentially useful for triage and current threshold, but no score is exposed today and raw token/softmax scores are not calibrated. | Requires candidate scoring/classifier design, disjoint calibration/validation evidence, reliability checks by class and use case, and a newly justified threshold. Existing reviewed data are small/provenance-limited for strong calibration claims. | Future option; do not emit a pseudo-score now. |
| C — Classifier plus separate changed-element extraction | Clean separation if product can specify exact spans/entities and obtain reviewed extraction targets. | Existing labels do not supervise the extractor; current title/impact dependence can instead use source text or explicit unavailable state while extraction is postponed. | Postpone unless a measurable user requirement and annotation protocol are approved. |
| D — Full four-field generative model | Unsupported by reviewed targets; masking fabricated interiors does not remove teacher-forcing context mismatch. | Would require reviewed explanations and element targets with a precise rubric, plus independently validated/calibrated confidence semantics and factuality/extraction evaluation. | Not scientifically defensible with current data; no synthetic pseudo-ground-truth. |
| E — Hybrid: label-only model, Go-owned derived presentation, versioned API | Aligns model learning with available evidence while preserving backend authority and user-facing workflow where justified. | Requires explicit unavailability/provenance, redesign of numeric threshold and persisted representation, and coordinated versioned migration. | **Recommended target architecture.** |

## 8. Recommended Architecture

**Model responsibility:** Return exactly one validated six-class label for the requirement/message pair. It does not invent confidence, reasoning, or changed elements. A strict one-key result (or equivalent constrained class output) is the target; malformed output remains an error, not a postprocessing opportunity.

**Inference service responsibility:** Implement a *future versioned* label-only model boundary with exact label validation, model/version provenance, and clear errors. Keep the existing endpoint/contract unchanged until an approved migration; do not silently wrap a label-only output into four invented model fields.

**Go backend responsibility:** Retain requirement selection, project authorization, domain overrides, change/scoring rules, and save authority. Replace the current 0.35 model-confidence suppression only after choosing an explicit alternative such as review/abstention or a separately calibrated score; do not set a fake 0.5/1.0 to keep the branch running. Derive titles/descriptions from cited baseline/message content or deterministic rules with provenance, or leave them unavailable where a truthful derivation is impossible. Do not claim such text is the model's rationale. The backend can continue producing a useful change draft without claiming the model extracted changed elements.

**API response contract:** Use a versioned response that distinguishes `unavailable` from a measured zero, empty explanation, or known-empty element list. For example, a future direct response could carry `label`, nullable `confidence`, nullable `reasoning`, nullable `changed_elements`, and a per-field provenance/availability marker; `changed_elements: null` means *not assessed*, whereas `[]` would mean *assessed and none found*. This is a design illustration, not an implemented schema. The legacy four-field endpoint and clients cannot safely consume it unchanged. Project-analysis APIs may expose separately derived backend descriptions labeled as such.

**Persistence responsibility:** Preserve historical records as historical evidence. Version/source-tag future model results and backend-derived change text; represent absent scores as absent/nullable rather than zero percent. Continue storing the selected label and only defensible derived fields, with save-time authorization/validation. Do not retroactively convert old generated confidence or reasoning into calibrated evidence.

**Frontend responsibility:** Show the class decision, source-backed change context, and an explicit unavailable/uncalibrated state where applicable. Do not render `null` as 0% or an empty list as proof that nothing changed. Separate developer diagnostics from user-facing claims and preserve the change-request workflow only with honest source/provenance.

## 9. Model vs API Contract

The contracts **should differ**. A narrowly supervised model response can feed a richer API assembled from separately justified sources. That separation reduces generation and parsing failure surface without requiring consumers to mistake unsupported fields for model knowledge. It does *not* provide backward compatibility automatically: current Go decoding requires all four non-null fields and current TypeScript UI assumes a number for confidence (`server-go/internal/modules/drift/inference_client.go:99-134`; `client/src/features/drift/drift.types.ts:95-100`; `client/src/features/drift/DriftAnalysisPanel.tsx:326-342`). A versioned, explicit migration is required. Compatibility shims that fill fabricated values, or loosen the existing frozen acceptance gate, would defeat the point. Existing P1 and production behavior remain unchanged by this review.

## 10. Migration Surface

No changes are made here. An approved migration would have to address:

- **Inference:** `services/inference/runtime.py`, `contracts.py`, `app.py`, prompt/configuration, deployment and Python contract tests; distinguish legacy P1/four-field and new label-only versions rather than silently changing one.
- **Go/API:** `server-go/internal/modules/drift/inference_client.go`, `drift_service.go`, `drift_postprocess.go`, `drift_scoring.go`, `drift_model.go`, `drift_dto.go`, `drift_handler.go`, `drift_routes.go`; remove or replace the 0.35 dependency, define nullable/provenance semantics, maintain validation/authorization, and version direct/project responses.
- **Persistence/workflows:** Mongo `driftanalyses` documents and read paths; `server-go/internal/modules/change_request/change_request_service.go` and related draft views; historical schema/version handling without rewriting old evidence.
- **Frontend:** `client/src/features/drift/drift.types.ts`, `client/src/api/drift.api.ts`, `DriftAnalysisPanel.tsx`, `DetectedChangeCard.tsx`, `DriftHistory.tsx`, and change-request UI; no misleading 0% or empty-element fallbacks.
- **Evaluation/tests/docs:** Go/Python/frontend contract tests; `server-go/internal/modules/evaluation/evaluation_benchmark.go` and report types; `tools/verification/evaluate_raw_model.py`, `tools/phase3j_kaggle/phase3j.py`, prompt/packaging assumptions, and `docs/model-pipeline.md`/`docs/model-card.md`. Existing frozen P1, dataset partitions, gates, baseline/probe artifacts, and sealed final evidence must remain unchanged. A new contract requires a prospectively specified, separately versioned evaluation; its metrics cannot be reported as a pass of the old four-field gate.

## 11. Phase III-J Training Implication

**Outcome B: redesign the Phase III-J experiment before another run.** This does not automatically authorize or justify another fine-tune. The original oracle-requirement model already produced structurally valid output on 90/90 cases and 73/90 correct labels (macro-F1 80.89%) in Phase III-I; Phase III-I.5, a different stress setting, recorded 161/215 correct (macro-F1 75.89%) and meaningful removed/contradiction boundary errors (`docs/phase_iii_i_final_report.md:21-55`; `docs/phase_iii_i_5_final_report.md:55-75`). Those figures cannot be combined as one benchmark, but they show both a capable structural baseline and a possible semantic improvement target. The Phase III-J adapter's 0/124 structural result establishes failure of that *training/output-contract experiment*, not proof that retraining is inherently needed or useless. Earlier end-to-end analysis also found retrieval/selection limitations, which label tuning alone would not solve (`docs/phase_iii_g_final_report.md:46-58`).

Before any new model work: approve the target contract; compare a strict label-only original-model baseline on permitted development evidence, including per-class errors and relevant requirement selection; define a prospective label-only evaluation and expected product gain; then decide whether a training experiment is worth its cost. The AI-reviewed dataset provenance and small development partition constrain the strength of any claim. The current four-field acceptance gate is not weakened or repurposed, and no final-holdout sample is used for redesign, thresholds, or calibration.

## 12. Risks

- Removing a made-up confidence number without redesigning the Go filter could silently admit or suppress changes; migration must be atomic and tested.
- Reasoning is currently user-visible and can affect grouping, scoring, summaries, and change requests; dropping it without source-backed replacements can reduce usefulness, while continuing to generate it without supervision risks false rationales.
- A missing changed-elements list is not the same as a verified empty list. Backend-derived titles/impact need provenance and regression checks.
- Historical saved results contain old generated and heuristic values; consumers must not reinterpret them as calibrated outcomes after migration.
- A smaller JSON schema improves structural feasibility but does not guarantee class accuracy, requirement retrieval, or calibration. Any future threshold must be validated against its own specified evidence.

## 13. Final-Holdout Boundary

The sealed final holdout was not opened, enumerated, or used. It remains unavailable for architecture design, schema choice, calibration, thresholds, migration planning, or retrospective rescue of the rejected adapter. Frozen datasets/partitions, P1, gates, and historical artifacts remain unchanged.

## 14. Decision Required

**Approve or reject one target boundary before further model work: a versioned label-only model contract with Go-owned, provenance-aware presentation and explicitly unavailable unsupported fields.** If approved, a separate implementation/evaluation plan must be authorized; this review itself implements nothing and does not authorize training.
